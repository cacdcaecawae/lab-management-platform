# Agent Note: 文件上传走普通 multipart，存储只经过 Storage API（原 D11、D12）

Status: implemented

## 问题

原始数据文件可能很大。第一期部署在本地和校内网络，以后可能部署到云服务器、改用对象存储。

## 决策

- 上传用 Django 普通 multipart，单文件上限 2GB（`MAX_UPLOAD_SIZE`，Nginx 的 `client_max_body_size` 要同时调整）。
- 所有文件读写经过 Django Storage API（`FileField`）；开发和单机部署用本地目录 `DATA_ROOT`。
- 磁盘文件名由服务器生成（`datasets/<数据集id>/<uuid>`），用户文件名只存数据库，杜绝路径穿越。
- 入库时流式计算 SHA256；同一数据集内文件名唯一，重复上传返回 409，不覆盖。
- 下载只经过带权限检查的视图，`MEDIA_URL` 不对外路由。

## 曾考虑的替代方案

- **分片上传、断点续传、浏览器直传对象存储**：大文件和弱网络下更可靠；第一期先满足本地和校内网络，不做。
- **直接操作文件系统路径**：写起来更直接；但以后切换对象存储就要改业务代码。

## 后果

- 收益：切换 S3 兼容对象存储只需安装 `django-storages[s3]` 并修改 `STORAGES`。
- 代价与重访信号：**部署到带宽有限的云服务器之前，必须重新评估分片上传和断点续传**（开发手册 §9）。2GB 上传尚未实测。
