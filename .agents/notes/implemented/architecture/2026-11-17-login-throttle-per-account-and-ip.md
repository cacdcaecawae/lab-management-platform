# Agent Note: 登录限速改为按"账号 + 来源地址"计数

Status: implemented

## Problem

[登录限速](./2026-11-17-login-throttle.md)（原 D26）原来只按用户名计数：每个用户名每分钟 5 次，超过返回 429，不管密码对不对。对 `16c38ee` 的审计指出：

- 学号很好猜。任何人每分钟拿错误密码对某个学号试 5 次，本人用正确密码也一直是 429。写个小脚本就能让某个学生，或者要做采购终审的导师，一直登不上。
- 原笔记否掉"锁账号"的理由正是"别人可以故意锁住你"，而按账号限速在攻击者持续发请求时效果一样。

约束：全组可能共用一个校园网出口地址，不能退回只按地址限速（原 D23 被否的原因）。2026-11-17 用户确认按本方案改。

## Decision

- `LoginRateThrottle`（`backend/accounts/views.py`）的计数键改为"用户名 + 来源地址"，每个组合每分钟仍是 5 次。用户名照旧去空格、转小写。
- `REST_FRAMEWORK["NUM_PROXIES"] = 1`（`config/settings.py`）：DRF 取 `X-Forwarded-For` 的最后一段作为来源地址。`infra/nginx.conf` 用 `$proxy_add_x_forwarded_for`，最后一段就是连到 Nginx 的真实地址，客户端自己带的头只会出现在前面，换不出新的计数。开发环境没有这个头，退回 `REMOTE_ADDR`。
- Nginx 每个地址每分钟 60 次的兜底不变。
- README 部署一节写明：Nginx 前面再加一层反向代理时，`NUM_PROXIES` 要改成 2。

## Alternatives considered

- **保持只按账号计数**：最简单；但任何人都能让指定的人登不上，而导师终审依赖导师能登录。
- **只统计失败次数，登录成功就清零**：攻击者持续发错误密码时，本人第一次尝试之前计数就已经满了，照样 429。
- **按账号计数，上限放宽到每分钟 30 次**：锁人更费力，但脚本照样能做到；猜密码反而快了 6 倍。
- **失败几次后要求验证码**：既防猜也锁不住人；但要加验证码服务或依赖、改登录页，在校内几十人的规模下不值得。

## Consequences

- 收益：在别处对你的学号试错，锁不住你；同一出口地址下其他账号照常登录。
- 测试：`backend/accounts/tests/test_login_throttle.py` 改为按地址断言：同一地址第 6 次 429；同一出口下其他账号照常登录；换一个地址，同一账号用正确密码能登录；在 `X-Forwarded-For` 前面伪造地址不产生新的计数。新测试在旧代码上失败（换地址仍是 429），改后通过。
- 浏览器：没有走。验证实例没有 Nginx，所有请求都来自 127.0.0.1，看不出按地址区分的效果；只有后端测试覆盖。
- 代价：
  - 和你在同一出口地址后面的人仍然能锁住你。
  - 从很多地址猜同一个账号时，每个地址各有每分钟 5 次，只剩 Nginx 每地址每分钟 60 次和 Django 的密码规则兜底。
  - `NUM_PROXIES` 必须和实际代理层数一致：少了，伪造的头能绕过限速；多了，所有人共用一个计数。
- 设备并发模型检查：`config/settings.py` 在被覆盖的文件里，这次只改了 `REST_FRAMEWORK`，没动数据库设置；10 次运行全部符合预期，`SYNC` 更新为 `c38b47a`。
