# Agent Note: 修改设备状态时核对打开表单时看到的状态（残留问题 R1）

Status: implemented

## Problem

[F1 修复](./2026-11-17-equipment-edit-stale-status.md) 之后，[TLA+ 模型检查](../testing/2026-11-17-tla-equipment-booking.md) 的 `with-edits` 仍然找到反例，即残留问题 R1：

1. 管理员甲打开设备编辑框，看到"可用"，选了"维修"，还没保存。
2. 学生登记使用异常，设备变为"待检查"，工作台出现提醒。
3. 甲点保存。他明确提交了 `status: "repair"`，服务器照写，"待检查"被盖掉，工作台提醒消失。
4. 之后有人看到"维修"，改回"可用"。从头到尾没有管理员看到过这次异常，故障设备重新开放预约。

F1 的修复只能挡住"没改的字段被写回"，挡不住"明确提交的状态是基于旧画面做的决定"。4 个请求时还有同类路径：甲在"维修"时打开表单选了"可用"，乙先改回"可用"，学生登记异常，甲保存。

2026-11-17 用户确认要修，并要求修完继续开发。

## Decision

- **接口**：`PATCH /api/equipment/{id}/` 提交 `status` 时，必须同时提交 `status_seen`，即打开编辑框时看到的状态，缺了返回 400。新建设备时 `status_seen` 被忽略。
- **后端**：`EquipmentSerializer.update()` 已经在行锁下重读设备，之后比对：锁下的当前状态既不是 `status_seen` 也不是要设的新状态时，`Conflict`（409，`code` 为 `stale_status`），提示"设备状态已被改为“待检查”（你打开时是“可用”），请重新打开编辑框确认"。当前状态已经等于新状态时放行，写入同样的值不会盖掉任何东西。
- **前端**：`EquipmentFormDialog.vue` 只在状态改过时提交 `status`，同时带上 `status_seen`（打开时的状态）。收到 `stale_status` 时弹出警告、关闭对话框，并发出 `stale` 事件，设备详情页随之重新加载，管理员能看到最新状态和使用记录里的异常登记。
- **模型**：`EditUpdate` 在锁下做同样的比对，失败即回滚并返回 409。`with-edits` 的预期改为通过，`with-edits-no-repair` 删除。新增改坏的变体 `edit_skips_status_seen_check`，它让规则 2 失败。`break-form-sends-unchanged-status` 删除：有了服务器端的比对，表单多发没改的状态只会得到 409，不再破坏规则，这个变体已经证明不了什么。前端只发改过的字段，现在的作用是避免无谓的 409。

## Alternatives considered

- **整条记录的版本号（`updated_at`）比对**：能挡住所有字段的并发覆盖。但每次使用登记、每次别的管理员改备注都会让版本号变化，开着对话框的管理员保存时常被打回。这里只需要保护状态。
- **`status_seen` 可选，不带就不比对**：对现有调用更宽松；但只要有一个客户端忘了带，R1 就回来了。平台只有这一个前端，要求必带的代价很小。
- **提醒改为按"未处理的异常登记"计算，管理员点"已处理"才消失**：状态怎么改提醒都在，覆盖面更大；但要新增字段和"处理"操作，改动比本方案大。用户选了本方案。
- **409 时不关对话框，而是重新取设备、刷新表单里的状态**：管理员填的其他改动不丢；但对话框要再取一次数据，详情页也还是旧的。这种冲突很少，关掉重开更简单。

## Consequences

- 收益：管理员在旧画面上改的状态，不会再盖掉期间登记的"待检查"。验证结果：
  - 模型检查 `with-edits`（3 个并发请求，编辑可以改成任何状态）完整通过全部规则和死锁检查，共 57 万个状态。
  - `break-edit-skips-status-seen-check` 按预期违反规则 2。
  - 另外手动跑了一次 4 个并发请求的 `with-edits`（覆盖上面那条 4 步路径）：没有反例，40,354,153 个状态，用时 3 分钟。太慢，不放进 `check.sh`。
- 测试：
  - 后端新增 3 个测试：旧表单改状态返回 409 且状态不变；改状态不带 `status_seen` 返回 400；当前状态已等于新状态时放行。
  - 双连接竞态测试改为参数化，增加"改状态"一组：异常登记在 `get_object()` 和保存之间提交时返回 409。修复前，新增的 3 个失败用例都确认是红的。
  - 前端 `components.test.ts` 的"改状态时带 `status_seen`""收到 `stale_status` 时关闭并发出 `stale`"两个用例在修复前失败。
- 浏览器（verify-lab，2026-11-17）：
  - 管理员先打开编辑框选了"维修"，学生随后登记异常，管理员点保存。
  - 请求体是 `{"status":"repair","status_seen":"available"}`，响应 409 `stale_status`。页面弹出警告，对话框关闭，详情页刷新为"待检查"，使用记录里有这次异常；数据库里仍是 `needs_check`，修改历史里没有管理员的写入。
  - 管理员重新打开（表单显示"待检查"），再选"维修"保存成功，修改历史依次为 `available → needs_check → repair`。
- 代价：
  - 接口变化：以后接入的其他客户端改状态时必须带 `status_seen`。
  - 管理员遇到 409 时，对话框里其他未保存的改动会丢失，要重填。
- 不变：两个管理员同时改同一台设备的其他字段（不是状态）时，改同一个字段的，后保存的覆盖先保存的。
