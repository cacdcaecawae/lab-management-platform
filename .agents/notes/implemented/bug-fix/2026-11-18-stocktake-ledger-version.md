# Agent Note: 盘点使用追加账本版本拒绝旧基线

Status: implemented

## Problem

Issue #1：两个管理员看到库存 10，实盘均为 8，各提交差额 -2 后账面变为 6。只比较库存数值也挡不住先领用后退回的 ABA。

## Decision

读耗材时同一聚合查询返回库存及 stock_version（最大流水 id，空账本为 0）。盘点必须发送 stock_version_seen，后端在耗材行锁内重算版本并比较，不同则返回 409 stale_stock；普通出入库不要求版本。前端冲突后关闭旧表单并刷新，要求重新盘点，不自动更新版本重发旧差额。

审查发现原 Django admin 的 StockTxnInline 可写，破坏只追加前提；本修复将其设为只读并禁止增改删，保留查看与耗材元数据维护，纠错统一走盘点 API。此可见入口收窄使后台与原业务契约一致。流水不可修改或删除且所有 API 追加流水都先锁耗材；因此同一耗材的新流水必然改变版本，即使总库存相同。不同耗材的序列号跳号无影响，未提交/回滚事务不构成账本变更。版本和库存来自同一 SELECT，避免撕裂读取。后端先部署时旧前端缺 token 的盘点安全返回 400，需同步部署前端。

用户 2026-11-18 授权“继续审查，确定的，可以优雅的修复但是只能先pr”，本方案按授权实施，仅草稿 PR，不合并部署。

## Alternatives considered

只比较 stock 可兼容简单数值，但不能识别 ABA。新增自增 revision 列也可靠，但当前追加账本已有唯一递增 id，无需额外迁移和双写。服务端直接以 counted 覆盖现库存会抹去盘点期间合法领用，故不采用。

## Consequences

旧页面连续盘点、期间领用/入库和库存 ABA 都拒绝且不增加流水；当前版本盘点成功；空账本版本 0 正常；普通领用/退回/入库不变；前端发送打开时版本且 409 后不重试。

## Risks

MAX(id) 作为版本依赖当前只追加、不删除且所有写入持行锁的约定，未来允许导入/删除流水必须同步修改版本策略。SQLite 验证不能证明 PostgreSQL 行锁并发；后者及浏览器仍须在支持 socket 的环境运行。

## Verification

真实 DRF + SQLite ORM 通过旧版盘点、ABA、空账本、新版本重试、普通出入库、其他耗材不误伤和后台超管只读验证；新增 PostgreSQL 同版本并发盘点及 dashboard 回归用例，尚未在 PostgreSQL 执行。前端组件验证提交看到的版本和 409 后只刷新不重试。最终检查结果记录于 PR；不将 SQLite 当作行锁验证。
