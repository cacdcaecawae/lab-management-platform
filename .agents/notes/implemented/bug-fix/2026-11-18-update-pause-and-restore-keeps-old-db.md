# Agent Note: 更新前停站再备份，恢复保留原库到最后，依赖检查补上 from x import views

Status: implemented

## Problem

2026-11-18 的外部审查对 #9 提了四条，其中第 1 条的前半由[上一条修复](2026-11-18-server-script-success-guards.md)解决（Compose 启动失败不再报成功）。剩下的：

- **回退会丢掉更新期间保存的内容**：`update.sh` 先备份，网站照常运行；新版本已经迁移数据库却起不来时，回退用的是这份备份，备份之后用户提交的采购申请等会消失。
- **完整恢复过早删除原库**：`restore.sh` 换上恢复的库后马上删掉原库，再恢复文件。文件恢复中途失败（例如磁盘满了）时，原库已经没了。临时库固定叫 `restoring` / `before_restore`，开头先删同名库，上一次没恢复完留下的库会被误删。
- **成功只看网站能否响应**：审查还建议核对实际运行的镜像。shell 里导出的 `APP_VERSION` 优先于 `.env`，这时 `up -d` 成功、网站也能响应，跑的却还是旧镜像。
- **依赖检查漏掉 `from reports import views`**：检查器只看 `ImportFrom.module`，这里只得到 `reports`。

## Decision

- **更新**：拉取镜像之后、备份之前停止 backend 和 web，到新版本验收通过或退回完成才重新启动。备份没完成就重新启动原版本，不更新。成功的条件是三项都满足：`up -d` 成功、健康检查通过、`compose ps` 显示 backend 和 web 都是目标版本的镜像。
- **恢复**：
  - 数据库先恢复到本次专用的 `restoring_<时间>`，这一步网站照常运行；失败就删掉这个临时库并退出，什么都没变。
  - 然后停站，把原库改名为 `before_restore_<时间>`，换上恢复的库，再恢复文件、启动网站、做健康检查。全部通过才删除原库；任何一步失败都保留它，并提示它的名字。
  - 不再删除任何已经存在的库。
- 健康检查从 `update.sh` 移到 `server-env.sh`，更新和恢复共用。
- **依赖检查**：`from x import a` 按 `x.a` 检查；同一行的重复报错只留一条。

## Alternatives considered

- **只在更新期间禁止写入（维护模式）而不停站**：要在后端加开关和页面提示。更新本来就要重启，停站只多了备份的几分钟。
- **回退时不恢复数据库，改为让旧版本兼容新结构**：Django 的迁移不保证向后兼容，做不到。
- **文件先恢复到临时目录再整体替换**：文件恢复失败时能完全不动原文件，但要两倍磁盘空间，而磁盘满正是最可能的失败原因。现在的做法是保留原库、提示重新运行；重新运行时 `restic restore --delete` 会把文件补齐。
- **核对镜像改为在脚本里 `export APP_VERSION`**：只能防住这一种原因；核对实际运行的镜像，不论原因都不会误报。

## Consequences

- 更新时，从停站备份到新版本通过检查，网站都不能访问。更新前的那份备份是停站做的，数据库和文件是同一时刻的。
- 恢复失败后会留下 `before_restore_<时间>`，要运维确认后手动删除，命令写在 README"备份与恢复"。
- 验证：
  - 脚本测试新增 6 个（共 13 个），在 Linux 容器里运行。这 6 个在上一条修复的脚本上都失败，修复后全部通过。
  - 在本机一套真实的测试栈（PostgreSQL 17、restic 0.19.1）上走了恢复：备份后删组、删文件、加文件，恢复后全部回到备份时的样子，不留临时库和原库。用一个不含文件的快照让文件恢复失败：原库保留为 `before_restore_<时间>`，提示里有它的名字，README 里的删除命令可用，再用正常快照恢复成功。`compose ps --format '{{.Image}}'` 的实际输出与核对逻辑一致。
  - 没有在真实服务器上跑完整的 `update.sh`：它会切换仓库的提交，本机只用命令替身测过。
- 依赖检查加了两个用例；加严之后现有代码仍然没有违规。
