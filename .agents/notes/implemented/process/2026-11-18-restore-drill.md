# Agent Note: 每月自动恢复演练

Status: implemented

## Problem

开发手册第 7 节要求每月在测试机上还原一次，并抽查几条记录和文件是否完好，"没有做过还原验证的备份不算可靠"。`scripts/backup.sh`、`restore.sh` 已经有了（见[发版、更新与备份](../../implemented/process/2026-11-18-release-update-backup.md)），但 `restore.sh` 会覆盖正在运行的网站，不能拿来演练。

现在演练要人手动搭一套环境，大概率不会每月都做。另外，数据量到了 TB 级以后，每月把全部文件还原一遍也不现实。

## Decision

- `scripts/restore-drill.sh` 使用独立的 Compose 文件和随机项目名，只起无主机端口的 PostgreSQL，临时后端镜像只运行校验程序、不启动网站、不发送邮件。生产备份路径只读挂载到无网络的 restic 容器，且不使用会修改仓库的锁。设置 `BACKUP_REPO_ID` 时，在同一只读服务核对仓库身份，配了 `BACKUP_MOUNTPOINT` 则必须固定身份；不读取 NAS 主存储。
- 固定一个快照完整 ID；将数据库导出通过管道导入隔离库。检查已应用迁移是否被镜像识别（含替代迁移）及是否有待应用迁移，打印表行数和最近周报历史时间。
- 每一类上传的文件分别抽样（模型里每个 `FileField`：数据集文件、知识库版本、组会附件、采购附件、使用登记照片、成果全文、头像；修改历史里的旧文件名不算）。逐文件流式读回：表里有 SHA256 的校验 SHA256，只有大小的核对大小，都没有的只确认快照里有这个文件（`restic dump` 找不到会失败）。不保存样本文件、不打印文件名。一个附件都没有就如实注明未验证。原先只抽数据集文件和知识库版本，2026-11-22 扩到所有类别。成功、失败及可处理的中断都只清本次隔离项目；清理失败不报告成功。
- 手工传入与快照兼容的后端发行版本，不默认用仓库最新版。正式调度由运维按 README 设置。

## Alternatives considered

- 用生产 Compose 改项目名：仍可能发布端口，且生产 restic 的仓库挂载可写。
- 全量打开附件：数据达到 TB 级后，空间和恢复时长不适合例行检查。抽样不能证明每个文件都可还原。
- 在同一机器上验证真实服务恢复：本演练不使用生产恢复脚本。跨主机灾难恢复、实际 Web 验收和回退另做。
- 与备份并发运行：只读仓库无法登记 restic 锁，需避开 prune、check 修复及其他仓库维护；若遇并发删除，读取失败直接报错。

## Consequences

- 合成命令替身覆盖正常、样本缺失、样本校验错误、清理失败、项目名碰撞；覆盖迁移编号未知及替代迁移识别。无 Docker 环境，未实跑 Compose、PostgreSQL 恢复和真实 restic 只读挂载；未接入生产定时任务。
- 数据库仍需要足够的 Docker 存储容量；先检查空间，不能靠抽样降低数据库存储开销。仓库抽样不解决在线备份跨数据库与文件时点不一致。
