# Agent Note: 设备并发模型检查只看 settings.py 的数据库设置

Status: implemented

## Problem

`.claude/skills/verify-equipment-tla/scripts/check.sh` 把整个 `backend/config/settings.py` 列在覆盖范围里，只要这个文件有改动就返回退出码 2（"被覆盖的代码变了，要人工核对"）。模型真正依赖的只是数据库的事务行为：隔离级别（默认 READ COMMITTED）和没有开 `ATOMIC_REQUESTS`（见 SKILL.md 的"假设"）。

2026-11-18 一天里，三次与设备无关的改动都触发了它：新增 `workbench`、`system`、`specimens` 三个 app，以及 `APP_VERSION` 设置。每次都要人工核对一遍，再提交一条只改 `SYNC` 的提交。以后每加一个模块都会这样，提醒变成了噪音，真正改数据库设置的那一次反而容易被当成又一次例行公事。

## Decision

- 从原覆盖清单移除整个设置文件，用标准库 Python AST 比较 `DATABASES` 顶层字典、相关覆盖标记与环境初始化。支持项目当前的字面量和 `os.environ.get` 形式；不导入设置，不改变 Django 行为。无法识别时提示人工复核。
- 分别检查 HEAD、暂存区和工作区，避免工作区撤回暂存的数据库变动时漏报。保留 `SYNC=e731809`，不能读历史时退出 1；原设备业务文件保留逐文件比较。
- 仅判断本仓库这一设置文件中的常见配置结构，不是一般的 Python 副作用分析器。引入外部设置文件、动态配置、自定义数据库路由或数据库运行时变化时，仍须主动复核模型。

## Alternatives considered

- 按行用 sed 提取：不处理缩进、多行表达式或复用后的覆盖。
- 继续检查整个设置文件：简单，但普通应用配置重复触发复核。
- 执行 Django 设置：会读环境，并可能执行配置中的其他行为，不能用于纯比较。

## Consequences

- 完整克隆可读原 SYNC；未更新它。隔离测试覆盖纯格式、普通应用设置、数据库选项、外部覆盖、环境别名、未知结构、以及 HEAD/暂存/工作区差异。
- 使用 SHA256 确认的官方 TLC 2.19，隔离工作树中普通应用配置返回 0，给默认数据库加入 `ATOMIC_REQUESTS` 返回 2；两次的 10 个场景均符合预期。
- 不修改模型、不改设备 API 或用户界面。无法识别的配置按变动报告，运行成功不替代数据库环境或持久化层验收。
