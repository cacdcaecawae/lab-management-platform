# Agent Note: 用 TLA+ 验证设备预约、使用登记与设备状态的并发交错

Status: implemented

## Problem

第二期的设备预约有四类请求会同时改同一台设备和它的预约：建预约、登记使用结果、取消预约、管理员编辑设备。代码靠行锁（`select_for_update`）和数据库约束防止冲突，见 [第二期设备与耗材](../feature/2026-11-17-phase2-equipment-and-consumables.md)。

平台对用户的承诺是：**登记使用异常后，设备转为"待检查"，在管理员处理之前不能再建使用预约。** 这条被打破时，有故障的设备会被继续预约使用，管理员工作台的"待检查"提醒也会消失。

现有测试一次只走一个请求，第一期审查留下的"真实并发测试"缺口一直没补；请求交错的组合很多，手写测试覆盖不到。

## Decision

- 项目技能 `.claude/skills/verify-equipment-tla/` 用 TLA+ 模型检查器 TLC（tla2tools v1.7.4，即 TLC 2.19；本机 `~/.tlaplus/tla2tools.jar`，脚本核对 SHA256，jar 不入库）穷举交错。`bash .claude/skills/verify-equipment-tla/scripts/check.sh` 约 25 秒跑完 9 次 TLC，把结果和预期比对。
- 模型 `spec/EquipmentBooking.tla` 中每一步对应一条访问共享行的 SQL 语句，SKILL.md 里有逐步对照表。管理员编辑从 `EquipmentFormDialog.vue` 打开表单开始建模，因为表单打开时就把状态填进去，保存时整张表单一起提交。
- 检查 5 条规则：异常待处理期间不能新建使用预约；这期间状态不会变回"可用"；预约不会既被取消又被登记；每个预约最多一条登记，重复登记得到 409 而不是 500；锁等待不成环。第 4 条原定为"最多一条"，但一对一约束已经保证了这一点，所以改成也检查重复登记时不出现 500。
- 5 个改坏的变体（`Mutant`）各自让对应规则失败，每次运行都会重跑，证明检查还能失败。
- 不加进 `scripts/check.sh`：只在改到覆盖范围内的代码时运行，避免每个开发者都要装 Java。
- 技能记录覆盖的文件和同步提交 `SYNC`（当前值写在 `.claude/skills/verify-equipment-tla/scripts/check.sh` 和 SKILL.md 的覆盖范围表里，每次确认模型后更新）；被覆盖的代码有改动时，脚本以退出码 2 提醒。

## Alternatives considered

- **真实多连接并发测试（pytest + 多线程 + 真实事务）**：测的是真代码，不会出现模型和代码不一致；但只能覆盖测试里强行安排的那几种交错。现在用它在真实代码上复现模型找到的反例，不提交。
- **只靠数据库约束**："预约时段不重叠"已经由排他约束保证，模型只把它当作前提；但"异常后不能预约"牵涉设备状态和多张表，不是一条数据库约束能表达的。
- **耗材"库存不为负"**：只有一把锁，模型更小；收益低于设备预约，留作以后的第二个目标。

## Consequences

- 收益：建预约、登记、取消三类请求在 3 个并发请求的界限内没有反例（287,841 个状态）；找到问题 F1，并在真实代码上复现。
- **问题 F1（2026-11-17 已修复）**：管理员打开设备编辑对话框，学生随后登记异常（状态变为"待检查"），管理员再点保存，表单里旧的"可用"会被整行写回，之后学生又能建使用预约。只发 `{location}` 的 PATCH 也会出现：`get_object()` 不加锁读到"可用"，异常登记在 `instance.save()` 之前提交。修复见 [管理员保存设备时不再把旧状态写回](../bug-fix/2026-11-17-equipment-edit-stale-status.md)：表单只提交改过的字段，后端在行锁下重读。`check.sh` 改为 11 次运行，含编辑的两次完整检查通过，两个新变体证明修复的两半都不能少。
- **残留问题 R1（2026-11-17 已修复）**：F1 修复后 `with-edits` 仍违反规则 2。管理员在旧表单里主动选了"维修 / 停用"，保存时覆盖了期间被异常登记改成的"待检查"，之后有人把"维修"改回"可用"，没有管理员看到过这次异常。修复见 [修改设备状态时核对打开表单时看到的状态](../bug-fix/2026-11-17-equipment-status-seen-check.md)：改状态时必须带 `status_seen`，不一致返回 409。`with-edits` 现在完整通过。
- 代价与已知上限：
  - 通过只说明在界限内（1 台设备、3 个请求、3 个时间段）没有反例。
  - 前提是 PostgreSQL 的 READ COMMITTED 行为，以及每步一条语句的抽象。
  - 权限、邮件、照片、`/admin/` 后台、耗材都不在范围内。
  - 模型不读代码：代码改了要按 SKILL.md 更新对应步骤，长期偏差用 `/maintain-formal-verification-skill` 对齐。
  - `/statechart` 在 Windows 上跑不起来（要启动 `/bin/sh`），本机只能读 TLC 的 log。
