# Agent Note: 第三期：采购申请、两级审批、到货登记、报销与统计

Status: implemented

## 问题

会议纪要要求采购改为"管理员初审 → 导师终审"的两级审批，减轻导师的审批压力；报销要能统计，并定期提醒财务。开发手册第三期列出了功能、数据表和验收标准，审批规则见手册 4.3：

- 申请人不能审批自己的申请；初审和终审必须由不同的人完成。
- 管理员本人提交的申请跳过初审，直接终审。
- 审批通过后修改了金额或品名，要重新审批。
- 每一步审批都留记录：审批人、时间、结论、意见。

手册没有定的是：导师自己提交的申请由谁审、审批结论有几种、通过后由谁改单据、到货怎么和台账关联、报销要不要审批、统计导出什么格式、给财务的邮件怎么定时发。2026-11-17 用户对方案的 6 个待确认问题回复"全部同意"，即按推荐做法实现。

约束：

- 采购和报销是个人数据，沿用 [按课题组隔离](../architecture/2026-11-16-roles-and-group-isolation.md) 和 [越权返回 404](../architecture/2026-11-16-access-scope-404.md)：本人、本组管理员和导师可见。
- [管理员不能冒用导师身份](./2026-11-17-manager-scope.md)，终审只认 `role=advisor` 的账号。
- 审批会有并发（两位审批人同时点、申请人边改边被审），状态变化必须在行锁下检查，吸取 [F1](../bug-fix/2026-11-17-equipment-edit-stale-status.md) 的教训。
- 经费只做统计，不控制额度（手册待确认事项 5 的默认做法）。

## 决策

### 模块与数据表

新 app `procurement`（`backend/procurement/`），金额一律 `Decimal(12, 2)`，单位人民币元。接口见 `docs/api-contract.md`"采购与报销（第三期）"。

| 模型 | 关键字段与约束 |
|---|---|
| `Fund` 经费来源 | group、name、code（组内唯一）、owner（可空）、active、notes。组内公开，只有管理员维护；停用后不能再选，旧单据照常显示 |
| `PurchaseRequest` 采购申请 | owner、fund（草稿可空）、purpose、status、submitted_at；有修改历史；编号 `PR-年份-主键` 现算 |
| `PurchaseItem` 采购明细 | request、name、spec、quantity（正整数）、unit_price（不小于 0）、link。小计、合计都不入库，现算 |
| `Approval` 审批记录 | request、stage（初审 / 终审）、reviewer、verdict（通过 / 退回修改）、comment、total（审批人当时看到的合计）。只增不改 |
| `Attachment` 附件 | 属于一张采购申请或一条报销（数据库约束二选一）、kind（报价单 / 发票 / 其他）、file、name、size、uploaded_by。只收 PDF、JPG、PNG，单个不超过 20 MB；存储名由服务器生成；下载走带权限检查的 `/api/attachments/{id}/file/` |
| `Reimbursement` 报销 | owner、fund、purchase（可空，只能是报销人自己的申请）、category、amount（大于 0）、occurred_on、description、status、submitted_at、paid_at；有修改历史 |

另外：`Equipment` 和 `StockTxn` 各加可空外键 `purchase`（只能选本组"已到货"的申请；入库以外的流水不能带）；`ResearchGroup` 加 `finance_email`，由运维在后台填写。新依赖 `openpyxl==3.1.5`。

### 采购申请的状态

```
草稿 ──提交──▶ 待初审 ──管理员通过──▶ 待终审 ──导师通过──▶ 已批准 ──管理员标记──▶ 已采购 ──管理员标记──▶ 已到货
  ▲              │                     │
  └────退回（必填意见）/ 申请人撤回─────┘
```

- **提交**：用途、经费来源（可用的）、至少一条明细、合计大于 0。管理员提交的直接进入"待终审"。
- **审批**：初审只能管理员，终审只能导师，都不能审自己的申请；两个环节按角色分开，初审人自然不会是终审人。导师自己的申请在管理员初审通过后直接"已批准"。结论只有"通过"和"退回修改"，退回必须写意见；不想买了由申请人撤回。
- **并发**：提交、撤回、审批、修改、标记都先 `select_for_update` 锁住这张单再检查状态。审批请求带上 `status_seen`、`total_seen` 和 `submitted_seen`（审批人页面上的状态、合计和提交时间），和锁下的不一致就返回 409 `stale`，前端提示后自动刷新。所以审批人批的一定是他看到的金额，两位管理员同时初审也只有一次生效。
- **修改**：草稿由本人改；审批中要先撤回（直接改返回 409）；已批准、已采购时本人或管理员可以改明细（例如实际价格变了）。品名、数量、单价有变化才算改了审批内容：单据回到"待初审"（管理员的单回到"待终审"），审批记录保留，修改历史的原因写明改前改后。规格、链接、用途、经费来源的改动不重审。已到货后不能再改。
- **删除**：只能删从未提交过的草稿；提交过的留作记录。附件只在草稿时能删（后来放宽为"审批人没看过的可以删"，报销交财务后不能再传，见 [附件删除规则](./2026-11-17-attachment-delete-after-approval.md)）。

### 到货登记

管理员标记"已到货"后，新增设备、编辑设备和耗材入库的表单里可以选一张已到货的申请。设备和流水是组内公开数据，所以只内嵌 `{id, code}`，不暴露申请人和用途；采购申请详情（个人数据范围内）列出关联的设备和入库记录。不按明细自动生成台账。

### 报销

- 本人登记，可关联自己的采购申请；保存后对话框不关，接着上传发票。
- 不审批，状态由本人或管理员推进：待提交 → 已交财务（记 `submitted_at`，必须已有发票类附件）→ 已到账（记 `paid_at`）。已交财务后不能改、不能删；要改由管理员退回"待提交"，修改历史记下退回人。

### 统计、导出与通知

- 列表、统计、导出共用一组过滤条件（状态、类别、经费来源、人员、月份、日期范围）；统计按经费来源 / 类别 / 人员 / 月份分组，各组和合计都由数据库求和。导出 `.xlsx`：工作表"汇总"和"明细"。
- 工作台：管理员和导师看到"待我审批的采购"（管理员是待初审，导师是待终审）；申请人看到"被退回的采购"。
- 邮件：配置了 `EMAIL_HOST`（邮件配置后来挪到网页，现在指运维在[系统管理](./2026-11-17-system-settings.md)里启用了邮件）才发，在事务提交后发，失败只记日志。提交后通知管理员，初审通过后通知导师，退回（附意见）、终审通过、到货后通知申请人。
- 财务提醒：管理命令 `send_finance_reminder` 给各组的 `finance_email` 发"已交财务、尚未到账"的清单，由宿主机定时任务每周一 9:00 运行（README"生产式部署"）。管理员也可以在"报销与统计"里手动发：没配财务邮箱或发信邮箱时返回 409 `not_configured`，SMTP 出错返回 502 `mail_failed`。

### 前端

- 菜单"采购经费"：采购申请、我的审批（管理员、导师）、报销与统计、经费来源（管理员；路由 `meta.manager`）。
- 采购申请详情页一页兼顾新建、编辑和审批，操作放在固定在底部的操作栏；手机宽度下申请人、经费来源、提交时间、进度两两一行。
- 嵌套序列化器（明细）的错误是以行号为键的对象，`normalizeErrors` 会把它展开成消息；明细页把每行的错误显示在那一行下面。没有表单的按钮（交财务等）用 `showActionError` 显示服务器给的原因。

### 并发模型

`Equipment.purchase` 是在 `EquipmentSerializer.update()` 同一把行锁下写入的非状态字段，和"存放位置"一样，不改变 [设备预约的 TLA+ 模型](../testing/2026-11-17-tla-equipment-booking.md) 描述的交错；它只能选已到货（终态、不能删除）的申请，校验时那次不加锁的查询不会读到过期状态。模型检查在 `3ef63b4` 上重新确认，10 次运行全部符合预期，`SYNC` 更新为 `3ef63b4`。

## 曾考虑的替代方案

- **报销也走两级审批**：管控更严；但手册只要求记录和统计，报销本身由学校财务审核，平台再审一遍会重复。
- **审批流做成可配置的工作流引擎**：以后改流程不用改代码；但现在只有一条固定流程，引擎的代码量和出错面都远大于两个状态判断。
- **审批用"版本号"整单比对**：通用；但申请人上传附件这类无关修改也会打回审批人。当时判断只比对状态和合计金额就够了；此判断已被[提交批次校验](../bug-fix/2026-11-17-purchase-review-checks-resubmission.md)中的等额换品反例推翻。
- **设置终止性的"驳回"结论**：审批人能直接结束一张单；但"退回 + 申请人撤回"已经能表达，多一个终态就多一套"驳回后还能不能改"的规则。
- **统计导出只做 CSV**：不加依赖；但财务通常要 Excel，CSV 的中文编码和数字格式在不同版本的 Excel 里表现不一致。
- **用 Celery 或进程内调度器发每周提醒**：不依赖宿主机；但要多跑一个常驻进程，只为每周发一封邮件，不值得。
- **到货后自动按明细生成设备或入库记录**：省事；但品名和台账往往对不上（一张单里有探头、线缆、运费），由管理员手动关联更准确。
- **设备、流水里内嵌完整的采购申请（含申请人、用途）**：页面上信息更多；但设备和流水组内公开，会把个人数据带出个人范围。只内嵌单号。

## 后果

- 收益：
  - 采购从提交到到货有完整记录：每一步审批的人、时间、意见和当时的合计都在，改价后自动重审。
  - 审批人不会批到改动之前的金额：浏览器里验证过"审批人打开后申请人撤回改价重新提交，审批人再点通过被拒（409 `stale`）"。
  - 报销按经费、类别、人员、月份随时统计，导出的 Excel 合计与页面一致。
- 测试：
  - 后端 `backend/procurement/tests/test_procurement.py` 23 个：两级审批和角色、管理员与导师本人的申请、退回必填意见、撤回、过期审批 409、双连接并发审批只生效一次、批准后改价重审、到货冻结、组内和外组隔离、附件类型大小与下载权限、每一步的邮件和发信失败、到货关联、经费来源、报销状态与发票要求、统计与导出合计一致、财务提醒只列本组。
  - 前端：`PurchaseDetailView.test.ts`（审批请求带上页面上的状态和合计；退回不写意见不发请求；409 `stale` 后重新加载，改坏代码后两个用例变红）、`utils.test.ts`（按分计算合计、金额格式、嵌套错误展开）。
- 浏览器（verify-lab，2026-11-17，代码 `4692d22`）：`features/procurement.md` 和 `features/reimbursements.md` 全部子功能走通，证据在 `backend/var/verify-evidence/2026-11-17-procurement/` 和 `…-reimbursements/`。走查中发现并修复：明细逐行错误让保存按钮抛出未捕获异常；"交财务"缺发票时只提示"提交的数据有误"；修改历史里的时间是 UTC 原文；手机审批页信息排得太长；同名的"删除"按钮。
- 代价：
  - 新依赖 `openpyxl`（纯 Python，锁定 3.1.5）。
  - 每周提醒依赖宿主机定时任务；忘了配置就没有提醒，只能手动发。
  - 邮件仍依赖学校的 SMTP 账号（手册待确认事项 7）；真实发信只在自动化测试里用内存邮箱验证过。
  - 手机宽度下审批记录要往下滑一点才能看到全部。
  - 选项下拉只取前 100 条（经费来源、已到货申请、报销关联的采购申请），超过时要改成远程搜索（代码里有 `shortcut:` 注释）。
- 回滚：新 app 都是新增表；`Equipment`、`StockTxn` 只各加一个可空外键，`ResearchGroup` 加一个可空字段，删掉即可。
- 本期不做：经费额度控制和余额预警；与学校财务系统对接；多币种；发票真伪校验和 OCR；AI 工具费用自动汇总（第四期对接 Magpie 后再做）。

提交批次校验补充：只比对状态和合计不能识别“撤回、同价换品、重提”，该部分决定由[提交批次校验](../bug-fix/2026-11-17-purchase-review-checks-resubmission.md)取代；其余审批规则不变。
