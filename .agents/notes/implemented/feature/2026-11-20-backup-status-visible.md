# Agent Note: 备份结果可见：在"存储与备份"页显示最近成功的备份、最近的失败和恢复演练

Status: implemented

## Problem

运维现在回答不了"昨晚备份成功了吗"。

- `scripts/backup.sh` 和 `scripts/restore-drill.sh` 跑在宿主机上，由 cron 或运维手动调用。结果只写进日志文件，网站完全不知道。
- "系统管理 → 存储与备份"页只检查 NAS 能不能读，备份部分只有一句"请由运维在服务器查看备份任务日志和恢复演练结果"。
- 一键安装只打印每日备份的 crontab 行，装没装上没人提醒。没装、装错路径、仓库盘满了，备份都会静悄悄地停下，直到需要恢复时才发现。

2026-11-20 的发版评审（GPT）认为，这是首版最值得补的一项：比再加一个业务模块更能保护第一批真实数据。用户同意在通知全组录入真实数据之前（v0.1.1）补上，并在同日确认了下面三点：记在数据库里、阈值写死、演练往正式数据库写一行状态。

## Decision

**记录**：

- `system` 模块的第一个模型 `OpsRun`：类别（`backup` / `drill`）、是否成功、结束时间、快照编号、一句说明（最多 200 字）。每类只保留最近 200 条。
- 管理命令 `python manage.py record_ops_run <backup|drill> <ok|failed> [--snapshot 十六进制] [--detail 文字]`。
- `backup.sh` 的 EXIT 处理在每次运行结束时记一条：成功记快照编号和标签；失败记失败的步骤（检查备份仓库 / 导出数据库 / 写入备份仓库 / 清理旧备份）、标签和退出码。`--init`、`--repo-id` 不记。
  - 顺带补上两处：收到 INT、TERM 时以 130、143 退出（原来 Ctrl-C 打断导出后返回 0）；restic 没打印唯一的 `snapshot <id> saved` 时算失败（原来照样返回 0，只有 `update.sh` 会检查）。
  - restic 的输出用 `tee` 写到备份目录之外的临时文件，从中取快照编号；`update.sh` 仍然从 stdout 读到唯一一行。
- `restore-drill.sh` 的清理处理同样记一条：通过时记快照前 8 位和"附件校验：N 项"，失败时记退出码。参数、环境文件、挂载点检查在安装清理处理之前就退出的情况不记，由"逾期"暴露。
- 记录都用一次性容器 `docker compose run --rm --no-deps -T backend python manage.py record_ops_run …`，不用 `exec`：`update.sh` 在 backend 停着时备份。共用函数 `record_ops_run` 在 `server-env.sh`；演练脚本不加载它，自己按同样的方式调用正式部署的 Compose 配置（`COMPOSE_FILE`，默认 `infra/docker-compose.prod.yml`）。
- **记录失败绝不影响任务本身**：输出全部丢弃，只打印一行"结果没能记到网站上，不影响这次任务本身"。

**显示**（只有运维账号能看，沿用 `/api/system/storage-status/`，字段见 `docs/api-contract.md`）：

- 最近一次成功的备份：时间、快照、标签。从来没有成功过时显示"尚无成功备份：确认已按安装结束时的提示加了每日定时任务"。超过 26 小时没有成功的备份时标"逾期"。
- 最近一次失败：比最近一次成功新时红字，否则灰字。
- 最近一次恢复演练：通过 / 失败、时间、快照、说明。距最近一次通过的演练超过 35 天时标"逾期"；从没演练过时，从第一次成功的备份算起。这样刚装好、刚备份完时不会立刻因为"没演练过"标需处理，一个月后才提醒。
- `attention`：备份逾期或当前失败、演练逾期或最近一次失败、NAS 不可用，任一成立。"系统管理"页打开时就请求一次，标签名变成"存储与备份 · 需处理"，和"版本 · 有更新"一样（2026-11-22 起系统管理拆成侧栏六页，改为侧栏"存储与备份"后面标红色"需处理"、"版本"后面标蓝色"有更新"，见[运维界面拆成侧栏六页](./2026-11-22-ops-pages.md)）。NAS 不可用时文件操作已经暂停，也算需处理。
- 阈值写死在 `backend/system/storage.py`：26 小时（每天 2:30 的定时任务加两小时余量）、35 天（开发手册每月一次）。

**不做**：逾期时发邮件、在网页上触发备份或演练、历史列表。表里留着历史，以后要做时可以直接用。

## Alternatives considered

- **把状态写进数据卷里的文件**（`/data/status/backup.json`，由 restic 容器写，后端读取）— 不需要数据库迁移；数据库坏了也能写。但在 NAS 模式下，`/data` 是 NAS 上的目录，NAS 断开时同样写不进去。要保留历史，还得在 shell 里读改写 JSON；后端也要处理文件写到一半的情况。数据库方案能用现有的模型、测试和管理命令写法，以后做邮件提醒可以直接复用现有的提醒任务。
- **网站自己去读 restic 仓库**（后端容器挂载备份仓库、知道备份密码）— 不需要备份脚本配合，结果最准。但要把备份仓库和它的密码交给对外服务的网站进程，网站一旦被攻破，备份也跟着暴露。
- **只在宿主机检查，靠邮件或日志告警** — 不改网站。但运维仍然要上服务器才能知道结果，正是原来的问题。
- **在一键安装最后自动加上 crontab** — 能减少"忘了加定时任务"。但改用户的 crontab 属于替用户改系统配置，各发行版 cron 的环境也不一样。现在的做法是打印出来让运维自己加，再由页面上的"尚无成功备份 / 逾期"把漏加暴露出来。
- **演练从没做过就立刻标逾期** — 规则最简单，但刚装好、第一次备份成功后页面仍是"需处理"，运维会习惯性忽略这个标记。

## Consequences

- 每次备份和演练多启动一个一次性的 backend 容器，多花几秒。
- 从 v0.1.0 更新到这一版时，更新前那次备份由旧脚本执行，不会记录；更新完成后的下一次每日备份开始记录。
- 时间按服务器时钟计算。服务器时钟不准时，"逾期"会误报或漏报。
- 数据库或 Docker 本身坏掉时一条也记不上，靠"逾期"暴露，最晚 26 小时后可见。
- 恢复演练原来完全不碰正式部署，现在会往正式数据库写一行状态（不碰业务数据）；正式网站停着时只打印提示。
- 验证：
  - 后端：管理命令（参数校验、每类只留 200 条）、刚装好、成功后需处理消失、27 小时逾期、失败后再成功、演练从第一次备份起算和失败、NAS 不可用算需处理、非运维 403。
  - 前端：刚装好、成功加旧失败加通过的演练、逾期加当前失败、重新检查 NAS。
  - 脚本（WSL）：`backup.sh` 成功记快照和标签、用一次性容器；仓库读不到、导出失败、导出时 Ctrl-C、没有快照编号四种失败都记步骤和退出码；记录失败时备份仍返回 0。`restore-drill.sh` 通过、各种失败和记录失败。这些新用例在改动前的脚本上全部失败。
