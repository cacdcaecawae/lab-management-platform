# Agent Note: 数据集用版本码，记录提交时固定所引用的版本（原 D25，取代 D22）

Status: implemented

## 问题

第一期审查 M2：实验记录、处理记录、周报提交后锁定，但它们引用的数据集还能追加文件，导致导师审过的记录所引用的数据还会变。同时，学生需要在提交之后继续往同一个数据集里追加数据。

## 决策

- 数据集的版本码像 git 一样计算：把文件清单按文件名排序，每个文件一行"SHA256 + 文件名"，再对整个清单算 SHA256（`backend/datasets/versions.py` 的 `digest_of()`）。版本码只取决于数据集里有哪些文件，与上传顺序无关。文件不能修改；没被非草稿记录固定的文件本人可以删除（[科研记录二合一与项目内共享](./2026-11-25-research-records-merge-and-project-sharing.md)），所以数据集的版本随新增文件或删掉这类文件而变，已固定的版本不受影响。
- 实验记录、处理记录、周报提交时，`pin_versions()` 为每个引用的数据集记下 `{数据集 id: 版本码}`，并用 `DatasetSnapshot` 保存那个版本的文件清单；文件清单相同的快照会复用。版本码和文件清单来自同一次查询，提交时如果正好有上传在进行，也不会对不上。
- 实验记录、处理记录退回后清空所固定的版本，草稿跟随数据集的最新文件；每次提交（包括周报补充后再提交）都会重新固定。
- 按版本码查看当时的文件清单：`GET /api/datasets/<id>/files/?version=<版本码>`。

## 曾考虑的替代方案

- **冻结被已提交记录引用的数据集（原 D22）**：被引用的数据集不能改名、不能追加文件，检查在 `ensure_not_frozen()`。实现简单，审过的数据一定不变；但学生不能再往同一个数据集追加数据，数据有误只能新建数据集。已被本方案取代，相关代码已删除。

## 后果

- 收益：学生可以继续追加数据；复现时按版本码取当时的文件。
- 代价：每次提交可能新增一个快照及其文件清单；数据集名称等元数据不在版本码里。
- 处理记录的脚本和结果也是数据集（见 [处理记录复用数据集](../architecture/2026-11-16-runs-reuse-datasets.md)），同样按版本固定。修改历史和"提交后锁定"见 [修改历史](../architecture/2026-11-16-change-history.md)。
