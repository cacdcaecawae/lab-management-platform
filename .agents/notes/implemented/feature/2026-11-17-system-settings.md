# Agent Note: 系统管理页：邮件、课题组、账号

Status: implemented

## Problem

开发手册第 5 节的菜单里有"系统管理（运维可见）"，一直没做。在这之前，运维的工作都要登录 Django 后台 `/admin/`，有的还要登录服务器：

- **邮件**：SMTP 服务器、账号、授权码写在服务器的 `.env` 里，改了要重启后端。发送失败只写日志，也没法先发一封试试。第二、三期的通知和财务提醒，一封都没真正发出过。
- **课题组和财务邮箱**：只能在 `/admin/` 改。报销页没填财务邮箱时，提示的是"请联系运维在后台填写"。
- **导师和管理员账号**：按[管理员权限范围](./2026-11-17-manager-scope.md)的决定，只能由运维在 `/admin/` 开通、停用、重置密码。

用户先提出邮件要有设置页（参照 sub2api 那种在网页里配置 SMTP、能发测试邮件的页面），又提出应该有一个"系统"标签集中设置。讨论时用户问过 `/admin/` 本身能不能用：它能增删改，但界面老旧，编辑页把"是否职员""权限组"等用不上的字段平铺在一起，也没有测试邮件；用户要求平台界面现代化，于是决定自己做页面。2026-11-17 用户确认"做系统管理页"，4 个待确认问题按推荐做法执行。

约束：

- 运维在业务接口里没有特殊权限（见[角色与课题组隔离](../architecture/2026-11-16-roles-and-group-isolation.md)）。系统管理页不能让运维看到科研记录、采购单、报销。
- 有些配置必须在后端启动前就确定，或者要和 Nginx、磁盘一起改，不能放进网页。
- 尽量不加依赖（见[最少依赖](../process/2026-11-16-minimal-dependencies.md)）。

## Decision

### 谁能用

- 只有运维账号（Django 超级用户）能用。新的权限类 `IsSuperuser`：已登录、`is_superuser`，并且已改过初始密码；其他账号 403。
- 运维账号通常不属于任何课题组：登录后直接进入 `/system`，菜单只有"系统管理"，右上角不显示课题组名。业务接口对它照旧返回 403 `no_group`。
- 如果运维账号同时属于某个课题组，它会看到本组的业务菜单，外加"系统管理"。
- `/api/auth/me/` 增加 `is_superuser`。前端路由守卫：非运维打开 `/system` 回到工作台；没有课题组的运维账号打开业务页面，会被送回 `/system`。

### 三个标签页

1. **邮件**
   - 单行表 `core.SiteSettings`（`pk=1`），字段：启用开关、SMTP 服务器、端口、加密方式（SSL / STARTTLS / 不加密）、账号、授权码、发件人地址，外加"最近一次发送失败"的原因和时间。
   - 授权码只写不读：接口只返回 `password_set`；留空保存表示不改。
   - 有修改历史（`django-simple-history`），历史表里没有授权码这一列。改了授权码的那次，修改原因记为"修改了授权码"。
   - 所有邮件都经过 `core/mail.py`：每封邮件发送时读取设置，按这些参数建 SMTP 连接，超时 10 秒。所以保存后立即生效，不用重启。
     - 发送失败时，用 `update()` 写入失败原因和时间，避免这次写入出现在修改历史里；之后发送成功一次就清空。
     - 业务代码检查邮件开关时只读不建：设置记录在运维第一次打开系统管理时才建，修改历史的第一条因此总是运维；还没有记录时视为邮件关闭。
     - SMTP 错误的原因写成"535 Error: authentication failed"这类易读形式。
   - **发送测试邮件**：用已保存的设置同步发送，邮件没启用时也发，方便先试再开。表单有未保存的改动时不发，提示先保存。
     - 失败时返回 502 `mail_failed`，提示"发送失败：<原因>"。
     - 没填 SMTP 服务器时返回 409 `not_configured`。
   - 启用时的校验：
     - 必须填 SMTP 服务器；
     - 账号不是邮箱地址时，必须填发件人地址；
     - 填了账号时，必须已有授权码，或者这次一起提交。
   - 切换加密方式时，端口跟着改为常用端口（465 / 587 / 25）；如果手动填过其他端口，就不再跟着改。
2. **课题组**：列表（含在籍成员数）、新建、改名、填写财务邮箱。名称重复提示"已有同名的课题组"。不提供删除，因为成员对课题组的外键是 `PROTECT`。
3. **账号**
   - 列出所有课题组的成员，可以按课题组、角色筛选和搜索；运维账号不在列表里，对它的修改返回 404。
   - 新建账号要填登录名、姓名、课题组、角色和初始密码，首次登录必须改密码；用户名重复返回 409。
   - 可以修改姓名、角色、邮箱、电话、研究方向，可以停用、启用、重置密码。
   - 状态列标出"未改初始密码"，另有"最近登录"列。

### 与方案不同的地方

- **账号的课题组建好后不能改**：方案原写可以改。把一个成员换到另一个课题组，会改变谁能看到他的实验记录、周报、采购和报销，项目成员等组内关系也会对不上。这类操作很少，留在 `/admin/` 里有意识地做。
- **财务邮箱由运维或本组管理员填写**：管理员在"报销与统计 → 统计"里点 "财务邮箱"（`GET / PATCH /api/reimbursements/finance-email/`，只限管理员），因为管理员比运维更清楚财务联系人是谁。方案里这是待确认问题 4 的推荐做法，已执行。

### 配置位置变化

- `config/settings.py`、`.env.example`、`infra/docker-compose.prod.yml` 删掉 `EMAIL_*`。
- 设备异常通知、采购各步通知、财务提醒（管理命令和手动按钮）都改为调用 `core.mail`。
- 第二期、第三期笔记里"配置了 `EMAIL_HOST` 才发"的说法，现在指"在系统管理里启用了邮件"。
- 发送失败照旧只记日志，不影响触发它的操作，同时记为"最近一次发送失败"。

### 留在 .env 和代码里的

| 配置 | 为什么不放进网页 |
|---|---|
| 数据库、`DJANGO_SECRET_KEY`、允许的域名、HTTPS cookie | 后端启动前就要用。填错了网页就打不开，也没法在网页里改回来 |
| 上传上限（2 GB）、数据目录、上传临时目录 | 要和 Nginx 的 `client_max_body_size` 以及磁盘一起改，只改网页会对不上 |
| 业务规则里的固定值：待登记提醒 14 天、照片 10 MB、附件 20 MB、预约可提前 5 分钟、报销类别 | 现在没人要改；哪天要改了再挪进来 |
| 财务提醒时间（每周一 9:00） | 由服务器上的定时任务决定 |

`/admin/` 保留，用于少见的操作，例如删除数据集、登记运维拷贝到服务器的大批量数据、给成员换课题组。

## Alternatives considered

- **继续用 `/admin/`，只在里面加邮件设置和"发送测试邮件"按钮**：改动最小，运维也只有一个入口。但 `/admin/` 的界面和平台不一致，编辑页字段多、容易点错，手机上也不好用；用户要求平台界面现代化，看过对比后选了自己做页面。
- **把业务规则的固定值（14 天、10 MB、20 MB 等）也做成设置项**：设置页会显得更全。但现在没人提出要改；每多一项设置，就多一组校验和测试，还要处理"改小之后已有数据怎么办"。
- **授权码用服务器密钥加密后再存**：数据库备份泄露时，授权码不会跟着泄露。但要加依赖 `cryptography`，换 `DJANGO_SECRET_KEY` 后要重新填授权码；而且备份和 `.env` 通常放在同一台服务器上。学校邮箱用的是可以作废重发的客户端授权码，所以选明文存储。
- **网页配置和 `.env` 并存，网页优先**：已部署的实例不用迁移。但配置有两个来源，出问题时不好判断用的是哪一份；平台也还没正式部署。
- **用 django-constance 这类通用设置库**：键值存储，自带编辑界面。但要多一个依赖，界面仍在 `/admin/` 里；而这里需要的只有一组邮件字段。
- **允许在系统管理里给账号换课题组**：方案原样。没选的理由见上面"与方案不同的地方"。

## Consequences

- **收益**
  - 学校邮箱账号一到，运维在网页里填好、点一下"发送测试邮件"，就知道能不能用；失败原因直接显示在页面上，不用翻日志。
  - 开通导师和管理员账号、建课题组，不用再进 `/admin/`。
  - 管理员能自己改本组的财务邮箱。
- **测试**
  - 后端 `core/tests/test_system.py` 覆盖以下内容：
    - 只有运维能用，业务接口对运维仍是 `no_group`；未改初始密码时被拦下。
    - 授权码不出现在任何响应和修改历史里，留空保存不改。
    - 启用时的三条校验。
    - 测试邮件：邮件没启用也能发；SMTP 返回 535 时返回 502，并记下失败原因；之后发送成功会清空。
    - 业务通知失败也会记成"最近一次发送失败"；运维打开系统管理之前，业务请求不会建出设置记录。
    - 课题组的新建、重名、改名、不能删除。
    - 账号的新建、重名、初始密码登录后要求改密码、筛选、不能换课题组、重置密码、停用后不能登录、运维账号 404。
  - 原有的邮件测试改为从 `SiteSettings` 读取设置。另加一个管理员改财务邮箱的测试。
  - 抽查了两处：把授权码改成可读，或者把权限放宽到任何登录用户，对应的测试都会失败。
  - 前端 `SystemMail.test.ts` 覆盖三点：留空不提交授权码；新填的授权码会提交；有未保存改动时不发测试邮件。
- **浏览器**（verify-lab `system.md`，2026-11-17）：
  - 运维登录后落在系统管理页。
  - 校验提示正常。
  - 保存请求的响应里没有授权码。
  - 测试邮件经由本机一个临时 SMTP 服务实际发出：授权码错时显示"535 Error: authentication failed"和最近一次失败，改对后发送成功、失败记录清空，临时服务收到了发件人和收件人正确的邮件。
  - 修改历史里只有"修改了授权码"，看不到授权码本身。
  - 课题组重名被拒。
  - 新建的导师账号首次登录被要求改密码；账号停用后，已打开的页面刷新即回到登录页。
  - 管理员进不了系统管理，接口返回 403。
  - 管理员能改本组的财务邮箱。
- **代价与风险**
  - 授权码明文存在数据库里，数据库备份里也带着它。
  - 网页能做的事变多了：运维账号被盗后能做的事和以前一样（`/admin/` 本来就能做），只是多了一个入口。
  - 测试邮件同步发送，SMTP 不通时最多等 10 秒。
  - 学校真实 SMTP 服务器（SSL / STARTTLS 证书、授权码规则）还没验证。
  - 换课题组仍然要去 `/admin/`。
  - 什么都没改就点"保存"，也会在修改历史里留一条没有字段变化的记录。
- **模型检查**：`equipment/views.py` 里设备异常通知改为调用 `core.mail`，仍在事务提交后、行锁之外发送；`config/settings.py` 只删了邮件设置，没动数据库设置。[设备预约的 TLA+ 模型](../testing/2026-11-17-tla-equipment-booking.md)不包含邮件，10 次运行全部符合预期，`SYNC` 更新为 `74595d4`。
- **回滚**：恢复 `settings.py` 里的 `EMAIL_*` 和三处调用，删掉 `core` 的 `0002_sitesettings` 迁移和系统管理页面。
