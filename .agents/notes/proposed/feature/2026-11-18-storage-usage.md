# Agent Note: 存储用量统计

Status: proposed

## Problem

开发手册第 9 节要求"摸清数据量"：试用期间每月在服务器上执行 `du -sh /data/raw`，再按"N 人 M 个月产生了 X GB"推算全组一年的数据量，用来确定数据盘和 NAS 的容量。这要运维记得每月登录服务器，而且 `du` 看不出是哪个组、哪个模块、哪个人产生的数据。

平台数据库里其实已经记着每个文件的大小：

- `DataFile.size`（原始数据）；
- `DocVersion.size`（知识库）；
- 组会附件、采购和报销附件的 `size`。

## Proposal

**接口**：`GET /api/system/storage/`，只给运维账号。

- `disk`：`shutil.disk_usage(MEDIA_ROOT)` 的总量、已用、剩余。
- `groups`：每个课题组的总字节数，按模块分：原始数据、知识库、组会、采购和报销、成果全文（成果全文目前没有 size 字段，先用存储接口的 `size()` 按需计算；数量多时改成在上传时记下大小）。
- `months`：最近 12 个月每月新增的字节数，按上传时间，按组分。
- `projection`：按最近 3 个月的平均值推算的未来一年新增量，以及按当前剩余空间还能用多少个月。

课题组管理员和导师另有一个本组的接口 `GET /api/storage-usage/`：按成员、按项目统计原始数据的大小，便于找出谁在占用空间。

**实现位置**：`system` app 按依赖规则只能引用 `accounts` 和 `core`，不能读各业务模块的表。所以这两个视图放在 `workbench` app（汇总层，可以引用所有业务模块），文件 `workbench/storage.py`：

- 运维那个接口用 `IsSuperuser` 权限，URL 仍挂在 `/api/system/storage/`（在 `config/urls.py` 里加一行）；
- 计算全部用数据库聚合（`Sum`、`TruncMonth`）。

**前端**：

- "系统管理"新增"存储"标签页：磁盘用量条、按组表格、12 个月表格，以及推算结论，例如"按近 3 个月推算，一年约新增 X GB，剩余空间约可用 Y 个月"。
- 管理员的"成员"页或工作台加入口，进入本组用量页面。

## Alternatives considered

- **定时运行 `du` 并保存结果**：能统计到不在数据库里的文件。但看不出模块和人；平台的所有上传都经过数据库，数据库里的大小已经足够准确。
- **扫描存储目录**：对 TB 级数据太慢，每次打开页面都扫描不可行。
- **放在 `system` app，并放宽依赖规则**：URL 更整齐。但会破坏"system 只碰账号和配置"这条边界，以后 system 会慢慢长成第二个 core。

## Acceptance criteria

- 后端测试：
  - 各模块文件大小正确归到各组；
  - 月份按 Asia/Shanghai 划分；
  - 推算公式（有固定数据时，结果可以人工核算）；
  - 只有运维能看全平台、管理员只能看本组、学生 403；
  - `disk` 用 monkeypatch 固定。
- 模块依赖检查通过（`workbench` → 各业务模块）。
- 浏览器：上传几个文件后，运维的"存储"页数字变化；管理员看到本组按成员的统计。更新 `features/system.md`，新增本组用量的功能文件。

## Risks

- 推算只是粗估：试用期数据少时偏差大。页面上写明依据和月数，3 个月不足时不显示推算结果。
