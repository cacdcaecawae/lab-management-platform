# Agent Note: 每月自动恢复演练

Status: proposed

## Problem

开发手册第 7 节要求每月在测试机上还原一次，并抽查几条记录和文件是否完好，"没有做过还原验证的备份不算可靠"。`scripts/backup.sh`、`restore.sh` 已经有了（见[发版、更新与备份](../../implemented/process/2026-11-18-release-update-backup.md)），但 `restore.sh` 会覆盖正在运行的网站，不能拿来演练。

现在演练要人手动搭一套环境，大概率不会每月都做。另外，数据量到了 TB 级以后，每月把全部文件还原一遍也不现实。

## Proposal

新增 `scripts/restore-drill.sh`，在服务器上运行，不碰正在运行的网站：

1. 读取 `.env`，另起一个 Compose 项目 `labdrill`：用同样的 `APP_VERSION` 镜像，单独的数据卷，不映射任何端口。脚本先检查项目名不等于正式项目，并且 `labdrill` 的卷不存在；有残留就先清掉，没有就新建。
2. 从 `BACKUP_REPO` 取最新快照（可以传快照编号）：
   - 数据库导出完整恢复到 `labdrill` 的数据库；
   - 文件只抽样恢复：在演练库里随机选 N 个 `DataFile` 和 `DocVersion`（默认 20 个），用 `restic restore --include` 只还原这些路径。
3. 检查：
   - `python manage.py migrate --check`：恢复出的数据库结构和镜像一致；
   - 关键表的行数（成员、项目、实验记录、数据集文件、采购申请），打印出来，和快照时间一起写进报告；
   - 每个抽样文件重新计算 SHA256，和数据库里记的值比较；
   - 最新一条修改历史的时间，看快照是不是最近的。
4. 打印报告，以"演练通过"或"演练失败：<原因>"结尾，退出码 0 或 1；最后 `down -v` 清掉 `labdrill`。
5. README 给出每月 1 日凌晨运行的 crontab 示例，输出写日志。

实现时复用 `scripts/server-env.sh`，用 `COMPOSE_PROJECT_NAME=labdrill` 区分项目。不要直接调用 `restore.sh`：它会停掉正式网站。

## Alternatives considered

- **全部文件都还原**：最彻底。但需要和正式数据一样大的空闲磁盘，TB 级时做不到；抽样加 SHA256 已经能发现"备份仓库损坏""文件和数据库对不上"这两类主要问题。
- **只跑 `restic check`**：只能证明备份仓库本身没坏，证明不了导出的数据库能恢复、恢复后能用。手册要求的是还原验证。
- **在另一台机器上演练**：最接近真实的灾难恢复。但要第二台机器能访问 `BACKUP_REPO`，目前没有。等有了 NAS 或第二台机器，再把同一个脚本挪过去跑。

## Acceptance criteria

- 在本机测试栈上（参照发版笔记的做法：本地镜像仓库、单独的项目名）：备份后运行演练，报告里行数正确、抽样文件 SHA256 全部一致，退出码 0；正式测试项目的容器和数据没被动过（运行前后 `docker compose ps` 和一条数据的值都一样）。
- 故意把备份仓库里某个文件对应的数据块改坏，或者在恢复前改坏数据库里一条 `sha256`，演练报失败，退出码 1。
- 演练结束后，没有遗留的 `labdrill` 容器和卷。

## Risks

- 演练期间多占一份数据库大小的磁盘，外加抽样文件。数据库很大时，要先确认磁盘空间：脚本开始前检查剩余空间，至少是数据库导出大小的 3 倍，不够就停。
- 抽样会漏掉单个坏文件。restic 自己的 `check --read-data-subset` 可以作为补充，按月轮换检查一部分数据，可以放进同一个脚本。
